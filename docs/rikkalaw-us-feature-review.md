# RikkaLaw-U.S. feature review and Kai merge map

**Reviewed:** November 22, 2026. **Donor:** RikkaLaw-US `88669c77dd402a19f253cb31d3ad1267ec5196ff`. **Evidence:** Source and CI review, not a new Android device run. This review proposes how to reproduce the working behavior in Kai; it does not change either app.

## What RikkaLaw-U.S. already does

| Area | Capability in RikkaLaw-U.S. |
|---|---|
| Matters and library | Create and delete matters with name and case details, upload multiple documents, switch auto-embedding on or off, manually embed pending files or re-embed a collection, remove indexed copies, and search within a matter. Files → Uploads has a general Library index with progress, failures, OCR needs, and a clear distinction between indexed and embedded. [Projects screen][projects] · [Library index panel][library] |
| Document intake | Copies originals into the app library, deduplicates by SHA-256 within the project, stores full extracted text and page offsets, and tracks copying, parsing, indexing, and embeddings. The parser handles PDFs, DOCX, PPTX, EPUB, HTML, images through OCR, and plain text; the visible Projects picker exposes a narrower list than the parser. [Ingestor][ingest] · [Projects screen][projects] |
| OCR | A dedicated vision model processes scanned PDF pages and images. The prompt asks for literal transcription, including speaker labels, line numbers, case identifiers, Bates and exhibit stamps, and explicit illegible/redacted markers. Successful OCR updates the index and can trigger embedding. These markings are requested as text, not guaranteed structured metadata. [OCR implementation][ocr] · [Index schema][index] |
| Chunking and search | Recognizes legal headings, paragraphs, sentence boundaries and cite spans; preserves normalized-text offsets and page ranges. Uses SQLite FTS5 BM25, trigram or phrase candidates, vector cosine similarity, a citation-key channel, weighted RRF, and optional reranking. Search modes are hybrid, keyword, exact, semantic, and citation. [Chunker][chunk] · [Index][index] · [Retriever][retriever] |
| Agent access to records | Tools list/create matters, ingest a file, search, read by page, OCR, collect grouped authorities, and compare a quote to indexed sources. A close quote match is reported separately; the donor's “verbatim” label still permits normalization and specified omissions, so it is not the same as an untouched literal match. [Record tools][record] · [Retriever][retriever] |
| Public legal research | Native citation verification with per-cite results; CourtListener opinion and federal docket search, opinion retrieval with opinion types, and most-recent U.S. Code from GovInfo. Docket search is not a dedicated docket-detail tool; the current U.S. Code endpoint is not a historical statute-version verifier. [Citation verification design][legal] · [Public research tools][court] · [Roadmap][road] |
| Drafting and export | Bundled § 2254 and § 2255 petitions, legal memorandum, and public-records request templates with a workspace Python DOCX path. A native OOXML writer also generates Word files without the sandbox, including caption, headings, tables, numbered paragraphs, real footnotes and page numbering. The native default is 12 pt Times New Roman and double spacing; the writer does not automatically build a Table of Authorities from the draft citations. [Drafting blueprint][legal] · [DOCX writer][docx] · [Roadmap][road] |
| Model and provider choices | Settings include separate chat, fast, translation, OCR, embedding, rerank and compaction slots; experts can carry their own model. The retrieval clients support OpenAI-compatible/NVIDIA embeddings, Gemini API-key embeddings, and generic or NVIDIA reranking. The roadmap identifies Gemini API and OAuth, OpenRouter, Groq and NVIDIA among the built-in providers, with custom OpenAI-compatible endpoints. [Model settings][models] · [Model clients][clients] · [Roadmap][road] |
| Agent runtime and memory | Inherited platform features include reusable Researcher, Verifier and Drafter roles, per-expert settings and memory; an optionally retrieved Markdown knowledge base and corpus importer; long-run context management, tool-output spilling, retry and foreground keep-alive; usage attribution and budgets; tool discovery controls; and workflow step outputs and secrets. These are capabilities to compare with Kai's existing chat, continuity and Objective runtime, not a requirement to replace it wholesale. [Legal blueprint][legal] · [Inherited Pure feature reference][pure] |
| Workspace and integrations | PRoot or Termux, legal bootstrap profiles for research, drafting, OCR and eyecite, with background progress and logs. Web search/fetch, MCP with header auth and OAuth, and reauthorization are documented; the roadmap still calls out real-server OAuth end-to-end testing as open. [Legal blueprint][legal] · [Roadmap][road] |

The repository has unit-test assertions for legal chunk boundaries, citations, quote matching, RRF, vector encoding, and rerank URLs ([legal RAG tests][tests]). The GitHub Actions [debug APK run][apk] and [JVM-test run][ci] provide build and automated-test evidence, not fresh validation of every device workflow or live provider. The donor's [roadmap][road] also leaves chat-to-matter binding, historical/expanded authority lookups, the unified verification report and automatic Table of Authorities unfinished.

## What to reproduce in Kai

**One matter workflow, not a second assistant app.** Open a matter, upload material through the existing composer or library, see which files are searchable, search or ask in the usual chat, and open the original source from each result. Keep matter records, public law, and code in separate collections with `matter_search`, `law_search`, and `code_search`. Keep Kai's existing shell/terminal and sandbox rather than building another one. The installed build has Ubuntu according to the user; the audited public Kai source shows Debian and Alpine in its selector and an existing Android shell tool. The discrepancy is a build/ref identification question, not a requirement to add a distro in this merge ([Kai distro source][distros], [Kai Android tool registration][shell]).

| Stage | Kai requirement |
|---|---|
| Ingest and preserve | Keep the original file and a raw page-level extraction/transcription; index a separate normalized copy. Store a stable source ID, content hash, extraction method/version, page-image index and printed page labels separately. Capture typed transcript page/line/speaker and Bates, ECF, docket and exhibit anchors, with a link back to the matching original page. Unknown coordinates remain unknown; describe photos separately from verbatim OCR. |
| Structure-aware semantic chunks | Split at section, heading, paragraph, page and transcript speaker/line boundaries before combining related units by semantic cohesion. Protect citations and quote spans with tested boundary rules. Keep a bidirectional map from each searchable chunk to exact raw source offsets. The donor is a strong structural baseline, but its boundaries are heuristic and its offsets refer to normalized text ([donor chunker][chunk]). |
| Scope and candidate retrieval | Derive the active matter and permitted collection from app context rather than trusting tool-provided project names. Filter by collection, document, document type, court/jurisdiction, date, docket, and applicable page/line, Bates, ECF or exhibit ranges **before** ranking or sending candidates to a provider. Query SQLite FTS5/BM25 and dense vectors as independent channels; add exact phrases and normalized identifiers for cites, dockets, Bates and code errors. An empty authorized scope must never become an all-matters search. The donor's empty-list behavior differs across retrieval channels ([donor index][index]). |
| Rank | Fuse ranked lists with RRF, then score a bounded candidate pool with the user-selected cross-encoder: it sees the query and each candidate passage together. Preserve verified exact identifier/phrase matches so semantic ranking cannot bury them. Keep retrieval provenance, exact-span matches, and rerank state visible. If a route is unavailable, show what ran and what did not rather than silently claiming full hybrid search. |
| Model routing | Independent Settings slots for **OCR vision**, **OCR cleanup** if used, **Embeddings**, and **Cross-encoder rerank**, separate from chat and Objective heartbeat. Identify vectors by provider/endpoint, model and indexing version rather than dimension alone, and show whether re-embedding is needed. Do not send a matter to a different provider because a chosen route failed. The donor stores the model label but only compares vector length during retrieval ([donor index][index], [donor clients][clients]). |
| Agent workflow | Make retrieval iterative: the model searches the scoped collection, opens adjacent pages or exact spans, refines its query when evidence is missing, and cites the original source. Check factual assertions against the record and legal authorities against the law collection or public lookup. Save completed reads and findings to chat continuity or the Objective checkpoint so the next call can resume without rereading. |
| Non-blocking draft review | Distinguish citation existence, treatment, quoted wording, pinpoint and source role. A report should identify what could not be verified without altering the draft or blocking editing or export. Reproduce useful native or local export behavior to Kai's requested format, not the donor's defaults or its counsel-only prompts and disclosure rules. |

Local indexing does not mean all processing is local: a remote OCR route can receive page images, a remote embedding route receives chunk text, and a remote reranker receives candidate passages with the query ([OCR implementation][ocr], [Model clients][clients]). Show the chosen route in the matter's indexing status, distinguish local from hosted processing, and avoid silently selecting a hosted route for an upload.

## Merge order and verification

1. Build one vertical slice: create a matter, upload a mixed text/scanned transcript, run the selected OCR and embedding routes, then find an exact Bates/line span and a paraphrased passage. Open each result at the original page.
2. Test pre-ranking matter isolation, equal-dimension embedding models that must not be mixed, pinned exact hits after reranking, unavailable providers, and citations crossing page or chunk boundaries. Test re-upload and deletion by stable ID: removing an indexed copy should remove its chunks, embeddings, and cached results without touching the original outside Kai. Keep keyword/exact search usable during indexing and label that state.
3. Connect the same retrieval to Research, Draft, and Objective, then reuse the source coordinates in a report-only citation check and in filing exports. Verify Android through GitHub Actions and device smoke testing for the completed branch, not by compiling in the phone sandbox.

**Reuse behavior rather than source by default.** [RikkaLaw-U.S. is AGPL-3.0][rlicense] and [Kai is Apache-2.0][klicense]. Reimplement the functionality in Kai unless licensing for code reuse is resolved explicitly; do not assume donor files or tests can be cherry-picked while keeping an Apache-only distribution.
